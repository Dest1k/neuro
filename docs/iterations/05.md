# Iteration 5 — complete local work/proof/submit lifecycle

Date: 2026-11-11, Europe/Moscow. Preparation iteration 5 of 10.

## Completed result

The project now receives a synthetic job over actual loopback TCP, prepares its
real Pearl matrices, computes the full-K result, selects and independently
checks a winning tile, builds/verifies a real PlainProof and submits it through
the donor's wire serializer. A separate local peer validates the received bytes
with pinned official Pearl code before producing its test response.

The final CPU replay passed **15 scenarios and 17 official proof verifications**.
The combined CUDA/kernel/proof/network executable also compiled and linked for
SM120 and passed two real TCP scenarios with its explicitly selected CPU backend.
Physical GPU execution, Windows and external pool acceptance remain unobserved.

## Engineering changes

- Added immutable complete job snapshots and monotonic generations. A change to
  the target, certificate or any header byte invalidates old work even when its
  job ID is unchanged. Exact duplicate notifications do not restart computation.
- Added a bounded compute callback interface, cancellation checks, an independent
  selected-tile arithmetic check and a verified-result handoff. A generation can
  reach its submit sink only once; a failed send remains consumed and uncertain.
- Reused actual donor TCP/framing, notify parsing, authorize/submit serialization
  and Rust gzip code. A small local guard handles full JSON validity and exact
  typed fields before the donor extractors. The reference checkout stays clean.
- Added a real event-loop client with one asynchronous compute worker, exact
  pending IDs, reconnect/reset behavior and distinct accepted/rejected/unknown
  accounting. A received notify is processed while old computation is in flight.
- Added a Python TCP peer with its own issued-job ledger, bounded decoding and
  separate official verification of every received submission. Deterministic
  checkpoints make cancellation ordering observable without timing guesses.
- Added a real CUDA callback that owns/synchronizes its buffers and invokes our
  full-K kernel. The same host/proof/wire lifecycle accepts this backend. The
  replay has an explicit `--backend cuda` hardware entry point; default is CPU.
- Added the full replay to GitHub's proof job and retained the previous arithmetic,
  proof-corruption and independent fixture gates.

The donor's work key covers only job ID and the first eight header bytes. That
source finding motivated full snapshot identity. Code review also found that
a backend error could be erased by simultaneous cancellation; the corrected
coordinator preserves the error and the native client stops the worker process.

Review of the peer caught a background stdout parser failure which could lose
its exception on excessive JSON nesting. Reader errors now reach the scenario
verdict. An additional silent-peer scenario checks the actual ACK timeout,
separately from closing the connection without replying.

## What failures mean

The peer exercises ordinary success, exact duplicates, wrong response IDs,
deliberate rejection/stale replies, malformed frames/notifications, rejected
authorization, reconnect/encoding reset and job changes before computation,
after computation, after proof construction and after verification.

In the EOF-without-ACK and silent-open-connection scenarios, the native process
correctly exits 1 with `completed:false`, one unacknowledged submission and zero
accepted/rejected shares. The latter produces `submit_response_timeout` after
about three seconds in the recorded run. Those are successful negative tests,
not accepted shares or successful mining sessions.

No throughput comparison or revenue claim is made. All jobs have synthetic
headers, targets and seeds. Each generation gets one bounded first-zero-B
attempt; a continuous production search scheduler remains future work.
