## A real sequence of mining attempts

The pinned donor's zero-B worker mutates one A row on each attempt while
retaining earlier rows. Repeating the original first-attempt preparation would
therefore search the same state instead of advancing the donor's sequence.
The new adapter applies the genuine donor row-mutation function cumulatively,
keeps signal Bt zero, and derives commitments, noise and noisy matrices from the
resulting signals. A repeated row index overwrites that row's earlier contents.

Attempt 0 uses the supplied 32-byte root seed unchanged. For indices 1 through
63, the row seed is BLAKE3 of the ASCII domain tag
`neuro/zero-b/row-seed/v1`, the root seed and the index encoded as four
little-endian bytes. The domain tag has no trailing NUL. This defines a stable
reproduction contract without changing any historical attempt-zero vector.

The current implementation reconstructs cumulative signal state from the root
seed for each attempt. It does not yet cache prepared panels, update commitments
incrementally or overlap arithmetic with proof generation. The fixed replay seed
and finite attempt cap are a correctness baseline, not a production entropy
policy or evidence of sustained mining throughput. The full contract is in
`docs/attempt-search.md`.

## Work identity, cancellation and proof handoff

The coordinator requires consecutive indices starting at zero and pins the root
seed when the generation claims its first attempt. A skipped or repeated index,
a changed root seed, an index outside the allowed range or a concurrent second
attempt is rejected before another arithmetic call. An invalid request before
the claim does not consume an index; an already claimed attempt remains consumed
even if computation fails.

Each execution ticket owns an immutable attempt identity. Preparation reads the
captured root seed, and the verified-result seal binds the proof to that seed,
its index and the full immutable work ticket. Mutating a public result cannot
turn an earlier verified proof into a permission to submit another attempt.
Each attempt can invoke its submission sink once, including a failed or throwing
sink. Separate verified attempts within the same generation can each submit.

An exact duplicate job retains its generation and search progress. Replacement
work or a connection change invalidates earlier results and starts a new sequence
at zero. Cancellation checkpoints remain active during later attempts. A backend
exception remains an error even if invalidation occurs concurrently; the client
does not silently reuse a failed worker.

The TCP client adds `--max-attempts`, an explicit `--stop-on-attempt-limit` option
and an attempt selector for the existing cancellation fixtures. It runs one
arithmetic task and permits at most one pending submission. A miss advances the
index; a found proof waits for its exact acknowledgement or rejection before the
next attempt. The existing overall deadline and response limits still apply.
An exhausted generation can wait for replacement work, or explicitly finish
with `reason: attempt_limit` once no response is pending.

Reports retain the root seed, derivation policy, generation, attempt indices and
separate started/finished/submitted/accepted/rejected/unacknowledged outcomes.
The submission guarantee currently lasts for one coordinator lifetime. There
is no durable cross-process submission journal or automatic recovery of a share
whose acknowledgement was lost; those limits remain explicit.

BLAKE3 binding, independently implemented signal/noise formulas and scalar
integer arithmetic. It does not call the native candidate, proof generator or
official verifier. Checking is the default; writing expectations requires an
explicit `--write` invocation. Existing first-attempt fixture files are unchanged.

The new corpus contains 11 complete cases: attempts 0 through 7, the first row
collision at index 24, the final supported index 63 and attempt 0 after a header

noisy-matrix fingerprints, commitments, every transcript word and every final

A target selected from those independent results produces seven genuine misses
followed by a proof at attempt 7. This deliberately chosen fixture tests
continuation; its success frequency says nothing about network difficulty or
mining revenue.

The peer uses its own issued-job ledger and independent gold to check the actual

## Complete candidate identity

The iteration-6 remote worker checked its runner and entrypoint, which did not
prove that the remote kernel or another source file matched the controller's
candidate. `tools/candidate_manifest.py` now inventories the complete public
candidate: exact root file bytes, dirty additions and deletions, and all pinned
upstream files. It verifies pinned source content against the recorded Git trees;
an arbitrary ignore rule cannot hide a newly added source file.

Private settings, credentials, generated outputs and toolchains retain their
separate boundaries. The manifest has bounded file counts and sizes, validates
portable paths and rejects unexpected links and case collisions. Its identity
does not depend on the absolute checkout location. `docs/candidate-identity.md`
records the precise format, exclusions and source limitations.

The v2 remote request stages the manifest and standalone verifier alongside the
fixed worker. The worker checks complete candidate identity before the action,
again inside the action process and after termination, including failed or
timed-out actions. The controller requires matching request and candidate
identities in the returned evidence. Source deployment is still explicit: the
complete checkout must already be present on the target.

Windows build/run records now use complete source identity and inventory all
top-level `neuro_*.exe` outputs plus the official checker. Prerequisites must
identify the correct successful action, actual Windows execution and matching
source/binaries. CTest treats an empty test catalogue as an error. A final source
and complete binary comparison prevents an action from recording success against
an inventory changed during its checks. These checks bind evidence to a candidate;
they are not an atomic filesystem snapshot against arbitrary concurrent changes.

## The owner's existing SRBMiner

The physical `run-cuda` action now acquires an exclusive GPU ownership lease.
Builds and CPU checks leave SRBMiner alone. The ignored
`configs/gpu-owner.local.json` profile identifies the owner's executable and
exact `guided-setup.bat`, with file hashes and owner identity; the public example
contains no private connection information.

Before stopping the miner, the implementation identifies its exact process and
known launcher using the executable path, owner, process creation time and
desktop session. An independent interactive watchdog must first become ready
and demonstrate a visible launch path. The action then stops the configured
processes and checks that they have not remained or respawned before GPU work.

After bounded test processes exit, recovery launches the configured batch through
a separate interactive task in the owner's desktop session. The result records
the batch launch, visible console and observed miner process separately; a
successful task invocation alone does not satisfy restoration. The action uses
`try/finally`, and a failed or unresolved handoff prevents overall success. A
durable request journal and watchdog handle owner-process exit without blindly
starting another GPU action. A miner that was already stopped stays stopped.

This is source implementation awaiting Windows and owner-host observations.
Synthetic worker fixtures do not establish that the owner's interactive desktop,
actual batch, miner or GPU recovery works. A complete Windows/driver hang remains
outside SSH recovery. The private owner note for the iteration-10 directive now
includes the required existing batch launch; neither the private key nor the
private connection profile belongs in the public repository or archive.

reproduction contract. Preserve the complete work identity, root seed, next
