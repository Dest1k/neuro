## Native Windows proof and host path

The real Rust builder now has explicit native Linux x86_64 and Windows MSVC x64
profiles. Rust version/compiler commit, donor/official source pins and lockfiles
remain fixed. The Windows profile uses a release dynamic CRT; CMake requires the
same setting and rejects a target, profile, configuration or library mismatch.
Native system link libraries come from the actual target rustc output.

The socket component and its tests use WinSock on Windows. The tests still open
real loopback sockets and exercise the protocol; they are not replaced by a
Windows skip. The three existing GCC/Linux donor arithmetic differential targets
remain Linux-only. The proof corruption corpus and the complete TCP replay use
platform-correct executable names and the same independent official verifier.

MSVC also retained references from the donor's unused asynchronous dispatcher;
neither section elimination nor a tested whole-program optimization attempt
removed its three unsupported callbacks. CMake now applies a small recorded
patch to a separate byte-checked build copy, excluding that legacy reader and
its start entrypoint. The original connect/receive/serializer functions and
their genuine dependencies remain. Four preparation checks and inspection of
the compiled Linux object confirm the copy/repair boundary, the absent legacy
references and the retained bounded transport functions. The full Linux proof,
native and TCP gates were then rerun against this implementation.

`windows/ci.ps1` provides four fixed actions:

| Action | Work performed |
|---|---|
| `build-cpu` | Build the real Rust library, official checker and native CPU/proof/host targets |
| `build-probes` | Build that path plus our CUDA probes and combined SM120 host |
| `run-cpu` | Check Python controls, native tests, the proof corpus and complete TCP replay |
| `run-cuda` | Require matching build/CPU evidence, then run physical GPU correctness probes and CUDA replay |

The script enters an installed Visual Studio x64 development environment and
uses Ninja/Release. It records source and binary fingerprints; a changed source
or executable invalidates the next action's prerequisite. Each action writes
an unsuccessful marker before starting and only records success after all its
gates pass. A CUDA build does not label its CPU tests as GPU execution.

Actual Windows trials exposed PowerShell's null-string coercion in atomic report
replacement and Cargo's long path failure while fetching pinned CUTLASS examples.
The fixes preserve a real null argument and use a short writable Cargo cache.
The builder checks that cache before starting expensive dependency work. It does
not change the source pin, remove the dependency, patch the reference checkout,
change global Git settings or alter the system registry.

## Owned remote work and uncertain outcomes

`tools/remote_worker.py` takes an ignored private profile and dispatches only
`inventory`, `build-probes`, `run-cpu` or `run-cuda`. It requires the supplied key
and existing known-host record, disables agent/port forwarding and stages each
request in its own directory. It does not upload the private key or profile.
The target repository must already be present; packaging and source deployment
are part of the later handoff work.

Each request binds its ID, action, worker, process runner and fixed entrypoint.
The worker checks both its staged runner and the runner inside the checkout,
because the latter is what the fixed action loads. Reports for another request,
different code, missing output or an inconsistent exit status cannot satisfy a
gate. Inventory can diagnose an absent repository before attempting a build.

`windows/BoundedProcess.cs` puts a child in a Windows Job Object before resuming
it. Its lifetime and bounded output include owned descendants. The integration
fixtures exercise timeout, output overflow, a child outliving its parent,
argument quoting, nonzero exits, terminating exceptions and code mismatches.
Synthetic fixture success is labelled as worker validation, not miner execution.

After an interrupted SSH command, the controller makes one bounded attempt to
retrieve that request's report. It does not automatically submit the action
again. An absent valid report remains unknown. A failed transport also cannot
be converted into overall success merely because a later report says success.
The outer Job Object strengthens the Windows cleanup boundary; an operating
system/driver hang which stops Windows itself remains outside SSH recovery.

The owner supplied private connection instructions for the iteration-10
directive. The information has been retained separately under the name
`neuro-owner-handoff-iteration06.json`; its contents and any key must stay out
of this public repository. The key location/layout and actual connection have
not been inspected here.

## MiniMax policy and durable cost boundary

`minimax/minimax-m3` is now the provisional executor selected by the owner.
`openai/gpt-6.1-sol` remains an explicitly enabled fallback, disabled by default,
with its own smaller limit inside the shared budget. No claim about MiniMax's
actual CUDA coding quality is inferred from the price list or these tests.

`tools/neuroctl/budget.py` uses a SQLite ledger with transactional reservations:
reserve a full-price amount, permit dispatch once, then reconcile the final
usage. Cache discounts are recorded separately and do not increase the budget.
The selected limits are 64,000 input tokens, 8,000 output tokens, 200 attempts
and $5 per work session, within an initial $25 campaign. The supplied MiniMax
rates imply a maximum reservation of $0.007408 for that request envelope;
200 such requests would reserve $1.4816. These are calculations from the
owner's quote, not observed provider charges.

Reservations survive restart and cannot be dispatched twice. Missing, invalid
or incomplete final usage retains its hold and blocks new campaign dispatch.
Late complete usage may resolve an uncertain record; changing an already final
receipt is rejected. Paid retries require new IDs and new reservations. The
module also records actual overruns and stops further dispatch, rather than
discarding the excess to make the configured limit appear intact.

The actual DSH/provider transport is not connected. These limits protect calls
which use the boundary and obey its token/attempt contract; they do not cap
DSH requests that bypass it. The caller must retain the same database and
campaign/session IDs, disable hidden retries, and reconcile every paid attempt.
`docs/model-selection.md` gives the Python and CLI contracts and restart rules.

remain local peer results, not live pool shares.

The combined CUDA/proof/network target also compiles and links for SM120 on

The actual Windows runner passes 10 native tests, 20 real Rust tests, all

proofs. Its Python suite discovers 111 tests: 109 pass and 2 platform-specific
cases are skipped. The actual Windows process runner passes 23 checks; the
fixed whole-worker fixtures pass 55. Those fixtures validate worker behavior
and use a synthetic entrypoint; the separate native/proof/TCP gates validate
the miner components. The validation report includes the tested commit and CI URL.

Both pinned upstream checkouts remain unmodified. The root README remains
present and exactly zero bytes. No model API call, live pool connection,
owner-laptop connection, driver change or power-profile change was made.

## Direction for iteration 7

Advance the miner from one bounded first-zero-B attempt per generation to a
bounded multi-attempt search, preserving full work identity, cancellation and
the independent proof gate. Save enough attempt/seed state to reproduce a
candidate and compare a verified baseline without claiming GPU speed from CPU
measurements. Bind a complete candidate manifest to remote deployment/results
before comparing remote candidates: the iteration-6 dispatcher checks worker
and entrypoint identity, not the caller's entire source tree. Keep no-progress
limits and the existing cost boundary; do not
replace miner development with another agent framework.
