# Iteration 4 — real PlainProofs and the official verifier

Date: 2026-11-11, Europe/Moscow. Preparation iteration 4 of 10.

## Completed result

The project now generates real Pearl PlainProofs from its retained signal
fixtures and verifies the actual output with two paths: the donor's Rust FFI
and a separate executable using the pinned official Pearl implementation.
All three selected winners pass both paths. Their losing counterparts and
controlled corruptions are rejected as intended.

This is the first observed proof-generation/verification result in neuro.
It concerns dense PlainProofs with Merkle strips on synthetic jobs. Recursive
STARK generation, GPU execution, Windows and live pool shares remain untested.

## Engineering changes

- Added a bounded C++ adapter for jackpot selection, full-signal proof
  generation, block/subroot witness construction and genuine FFI verification.
- Added independently generated Python jackpot/hash/target vectors for the
  existing cert2, cert3 and rectangular cert3 jobs. Winner/loser selection
  covers the modified signal row in all six cases.
- Added `rust/pearl-proof-check` using official Pearl commit
  `0dbdb2ffd8b81193a5079bb67a59aecc10ad501c`, with its own locked Git dependency.
  The verifier never links the donor's vendored zk-pow.
- Added a reproducible Rust 1.99.1 build from an isolated donor source copy,
  optional CMake proof targets, an offline corpus exporter and a bounded
  cross-process verification runner.
- Added a separate GitHub proof job that rebuilds the actual implementations,
  checks independent expectations and runs the same negative-case corpus.
- Preserved the official Pearl ISC notice and documented 349 source-file
  comparisons, 28 changed files and locked registry dependency provenance.

The source audit found actual differences between the donor and official
verifiers, including declared tree-size, circuit and rank checks. The separate
official verifier was added in response; passing only the donor wrapper would
have left this compatibility question unresolved.

The complete independently expected Rust jackpot hash and all 16 message words
match for the selected proofs. The target boundary and the value immediately
below it are tested, as are zero target, real losers, incorrect certificate
derivation, changed header, modified leaf/root and corrupted witness data.
Structural tests bound malformed base64/bincode, dimensions, indices, buffer
sizes and an extreme row anchor before unsafe FFI entry.

The corpus runner additionally reads raw proof metadata and checks dimensions,
selected rows/leaves and commitment roots against independent fixtures. The
official process must fail at the expected stage. A crash, panic, timeout or
argument error is not counted as a successful semantic rejection.

The final reproducible build was deliberately run with an inherited
`CARGO_BUILD_TARGET=aarch64-unknown-linux-gnu`. Its explicit pinned x86_64 target
overrode that setting, produced target-specific artifacts and passed the
native/canonical checks. This guards against selecting an old host-default
binary after Cargo silently used a different target directory. Generated
source timestamps are also refreshed to prevent stale path-crate reuse after
an archived source pin changes.

Build durations in logs describe these particular CPU runs and cache states.
They are not a hash-rate measurement or a prediction for the laptop.

## Decision for iteration 5

Move to the host/backend job lifecycle and an offline pool replay. Connect job
identity, cancellation, arithmetic result selection, real proof generation and
the submission payload. Reject stale results when a job changes, preserve the
independent proof gates, and exercise malformed/expired jobs without a live
wallet or pool connection.

The final archive and DSH directive remain scheduled for iteration 10. No
reseller/model API calls were made in this iteration, and API cost enforcement
is still a later DSH integration task. The README remains deliberately empty.
